# 일반 채팅으로 이어가는 팀 모드

기준은 0.7.0 `10de95b8f1740d7fc112c398c1859f6e9d7a059c`다. 사용자는 짧은 설계 뒤 구현·검증·문서화를 자율 수행하도록 지시했다. main 게시·전역 설치는 범위 밖이다.

## 사용자 경로

팀 모드 ON 이후 일반 입력 하나가 기본 경로다. 리더는 관련 대화와 실제 요청·실행·파일·검증 상태를 읽고 직접 답변, 새 작업, 수정, 중단, 재개, 재검증, 후속 작업, 명시적 수락 또는 짧은 확인 질문을 선택한다. 사용자가 ID·내부 상태·메뉴를 알 필요가 없어야 한다. 일반 응답 영역에 중요한 진행과 전체 결과·검증·검토·실패 이유가 남는다. 입력과 포커스를 유지한다. 여러 요청의 결과는 이름과 현재 revision으로 구분한다.

## 선택한 구조

메뉴 명령만 자연어로 감싸는 변경은 결과 표시와 문맥 연결을 해결하지 못한다. 고정 writer/reviewer 분류를 유지하는 변경은 리더의 실행 판단을 반영하지 못한다. 이번 구현은 현재 Pi 확장 안에서 대화 기록, 리더 제안, 검증된 직렬 실행을 연결한다. 이는 사용자가 지정한 세부 구조가 아니라 요구를 만족하기 위한 구현 판단이다.

- 대화: 수신 사용자 텍스트와 사용자에게 보낼 답변·진행·결과를 안정된 ID와 요청/revision 출처로 저장한다. 리더에게 최근 관련 교환, 대기 확인, 수락 제안, accepted 후속 관계, 실제 단계/검증/검토를 제한된 문맥으로 전달한다. 질문도 관련 답변이 기록되며 모든 입력을 새 구현으로 만들지 않는다.
- 판단: 기존 read-only 리더가 지원 역할과 범위에서 직접 답변/확인 또는 직렬 단계를 제안한다. 개발·디자인·읽기 전용 검토의 순서와 범위·검증을 판단한다. 변경이 있으면 마지막 독립 검토는 필수다. 읽기 전용 작업은 수정 수락 없이 답변으로 끝난다.
- 실행: `stages`는 순서가 있는 task ID 목록이다. 현재 controller의 단일 실행 소유권을 유지하며 임의 병렬 쓰기나 가짜 completed/dependency를 만들지 않는다. 기존 결과 carrier와 최종 reviewer를 정규화하고 추가 단계는 aggregate scope와 stageAttempts로 묶는다.
- 변경: 리더는 수정할 단계와 이유를 선택한다. 사용자 지시로 기대 결과가 바뀌면 관련 검증 명령과 변경 이유를 기록한다. 이전 검증과 그 결과는 보존한다. 내부 검토의 수정 제안은 기존 검증 명령을 바꿀 수 없다. 정상 재개는 유효한 artifact checkpoint 앞의 성공 단계를 보존한다. 리뷰 실패는 실제 findings를 리더에게 돌려 필요한 수정·재검증·중단을 판단하게 한다.
- 전달: Pi의 공개 `sendMessage`와 `SessionManager.getBranch()`를 사용한다. custom-message details에 기록 ID를 넣고 실제 history에서 조정한다. API가 void를 반환하거나 비동기로 지연된다는 이유로 전달 완료를 추정하지 않는다. 불확실한 전달을 무조건 재전송하지 않는다. reload 뒤 실행을 재생하거나 같은 응답을 중복 기록하지 않는다.
- 수락: 명확한 사람의 현재 대화 turn에서만 가능하다. session/owner에 묶인 결과 제안과 요청 revision·단계 attempts·checks·scope·최종 review·artifact를 확인하고 기존 controller acceptance 검증을 거친다. 모호한 긍정은 수락하지 않는다. 확인 중 근거가 바뀌면 거부한다. 이미 수락한 기록은 바꾸지 않고 필요한 후속 요청을 연결한다.

## 실제 Pi 1.4 저장 경계

실제 실행에서 공개 get_entries의 custom_message는 메모리에만 있고 부모 세션 파일이 생성되지 않는 경우를 확인했다. Pi 1.4는 실제 user/assistant message가 처음 생길 때 세션 파일을 만든다. 따라서 getBranch에서 관찰한 전달과 디스크 내구성을 구분한다.

영속 세션 경로가 있으나 파일이 아직 없는 첫 실제 사용자 입력에 한해 공개 native 입력 경로를 사용한다. 부모의 불필요한 모델 실행은 공개 abort 경로로 막고, compaction·cache warming·연속 입력도 같은 경계에서 검증한다. 실제 OpenAI responses 어댑터를 로컬 HTTP 계수기로 검사하며 내부 어댑터 함수 호출과 외부 모델 요청을 구분한다. 실제 사용자 메시지가 저장된 뒤의 일반 입력은 기존 handled 경로를 유지할 수 있다. 명시적인 메모리 세션에 파일 저장을 강제하지 않는다.

부모 native 취소를 사용자 작업 실패로 표시하지 않기 위해, 오직 확장이 소유한 무내용·사용량 0의 제어 취소만 공개 message_end 변환에서 로컬 소프트웨어 제어 상태로 표현할 수 있다. 원래 취소 자료는 공개 audit entry에 그대로 남긴다. 변환 자료는 provider/api/model을 codexteams-local/control로 구분하고 원격 AI 응답·사용량·리더 답변·수락 근거로 계산하지 않는다. 실제 agent_settled 취소 결과는 유지한다. 부분 응답, 사용량 불명, 다른 실행의 취소는 변환하지 않는다. 이는 실제 사용자 입력 저장을 위한 가짜 seed가 아니며 전역 Pi 수정·private API·세션 JSONL 직접 생성은 금지한다. 재진입 시 선택 모델 보존과 실제 TUI 표시를 따로 확인한다.

## 호환과 범위

기존 0.7 요청·pair·accepted receipt를 새 reader가 읽어야 한다. shared packaged JavaScript validator와 타입을 함께 변경한다. 새 필드·단계·aggregate receipt는 엄격히 검증하며 과거 근거를 새 근거로 소급하지 않는다. 기존 복구·프로세스 종료·단일 작성자·필수 검토·인증·역할별 모델 규칙을 유지한다. 새로운 상태를 이전 버전 writer로 수정하는 호환은 주장하지 않는다. 새 프로젝트는 planner/designer에 Astra high, developer/reviewer에 Sol high를 사용한다. 저장된 명시적 프로필은 변경하지 않는다. Normal 서비스 모드는 요청 값이며 공식 wire mapping이 확인되지 않아 주입하지 않는다.

원본 작업트리, main, 전역 0.7 설치와 기존 Pi PID77936, FiveBeat, 설정·인증·상태는 보존한다. 검증은 새 작업트리와 작은 격리 Git 텍스트 작업에서 수행한다. 별도 검증 앱·daemon·외부 Codex 런타임은 만들지 않는다. 개발 버전은 0.8.0이며 게시하지 않는다.

## 완료 근거

자동 회귀는 직접 답변, 관련 문맥, 결과 이후 수정, 단계별 재개, 재검증 시 writer 비실행, 여러 대상 확인, 오래된 수락 거부, legacy 읽기, history 조정·중복 방지·입력 유지를 검증한다. 실제 Pi 일반 채팅으로 실제 리더와 담당자가 작은 작업을 수행하고 진행 중 변경과 결과 후 수정을 확인한다. 실제 응답 history와 TUI 표시를 확인한다. fixture 판단은 프로토콜 근거로만 보고한다. 테스트 수락은 격리 fixture로만 수행하고 실제 사람 수락과 구분한다.
