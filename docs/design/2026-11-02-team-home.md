# 팀 기본 화면 0.5.0

사용자는 명령과 세션 구조를 외우지 않고 실행 여부를 확인하고 다음 행동을 선택해야 한다. 기존 0.4.0의 프로세스 소유권, 읽기 전용 조회, 명시적 수락, 순차 쓰기와 복구 규칙은 유지한다.

## 결정과 범위

- `/teams`, root의 `/teams home`, 인수 없는 CLI TTY 시작은 같은 팀 기본 화면을 연다. headless는 상태와 명시적 명령을 출력한다.
- 화면 순서는 프로젝트 이름, 현재 상태, 작업 목록, 선택한 작업의 행동이다. 큰 내부 목표는 상세에서만 본다. 저장된 목표나 기존 제목은 수정하지 않는다.
- 상태는 실제 controller operation에서 만든다. 계획 생성, 작업 실행, 응답 대기, 도구 실행, 검증 실행, 중단 요청을 구분한다. 시작 후 시간과 마지막 관찰 시각은 실제 시각을 쓴다. 백분율과 ETA는 만들지 않는다.
- idle은 `실행 없음 · 결과 확인 N개`처럼 표시한다. 수락 수를 실행 완료 수처럼 표시하지 않는다. 검증 중에는 task.status와 별개로 `검증 중`을 표시한다. 소유자가 없는 미완료 기록은 `실행 여부 확인 필요` 또는 복구 상태로 표시한다.
- 짧은 상시 위젯에도 같은 현재 상태와 작업 제목을 표시한다. 120x30 터미널에서 핵심 상태와 행동을 읽을 수 있어야 한다. 상태와 선택은 색만으로 구분하지 않는다.

## 사용자 행동

| 작업 상태 | 기본 행동 | 추가 행동 |
|---|---|---|
| 실행/검증 중 | 진행 보기 | 중단 요청, 상세 |
| queued이고 의존 조건 충족 | 작업 시작 | 작업 내용, 상세 |
| 선행 결과 미수락 | 선행 결과 확인 | 작업 내용 |
| needs_review | 결과 확인 | 수정 요청, 결과 수락, 상세 |
| failed/interrupted | 실패 이유와 결과 확인 | 다시 시도, 수정 요청, 상세 |
| accepted | 결과 확인 | 상세 |
| 복구 필요 | 복구 내용 확인 | 기존 복구 API를 통한 명시적 확인 |
| 작업 없음 | 새 목표 입력 | 상세/도움말 |

- 방향키와 Enter로 작업/행동을 고른다. Esc는 이전 화면 또는 닫기로 일관되게 동작한다. 화면에 현재 선택과 키 안내를 표시한다.
- 실행 완료로 진행 항목이 사라지거나 목록이 갱신되어도 선택한 작업은 task ID로 유지한다. 표시한 선택과 Enter가 여는 대상이 달라지지 않게 한다. 작업 행동도 렌더링 이후 바뀌었으면 새 대상을 추측해 실행하지 않는다.
- 결과 확인은 latest attempt의 최종 assistant text를 먼저 보여준다. tool transcript와 모델/effort/ID/사용량/원시 기록은 상세로 옮긴다. 결과 옆에 수정 요청과 결과 수락을 제공한다.
- 결과 본문은 화면 너비에 맞춰 줄바꿈하고 세로로 이동해 끝까지 읽을 수 있게 한다. 긴 한 줄의 뒤쪽을 잘라 사용자가 읽을 수 없게 만들지 않는다. 실제 operation이 있는 작업 행에도 `실행 중` 또는 `검증 중`을 표시해 상단 상태와 일치시킨다.
- 수정 요청은 입력을 받아 기존 resume API를 호출한다. 빈 입력/취소는 실행하지 않는다. 다시 시도와 작업 시작도 사용자의 명시적 선택으로만 호출한다.
- 결과 수락은 대상과 의미를 표시하고 명시적으로 확인받는다. 모델 성공, 테스트 성공, 화면 열기와 분리한다. 기존 결과를 자동 수락하지 않는다.
- 새 작업은 역할과 내용을 받아 queued로 추가한다. 추가만으로 실행하지 않는다. 기존 프로젝트 목표를 리셋하지 않는다.
- 일괄 `run()`은 실행을 요청한 시점의 작업 ID 집합만 실행 대상으로 삼는다. `launch()`는 계획이 저장된 직후의 집합을 사용한다. 현재 상태와 의존 조건은 매번 확인한다. 실행 중 뒤에 추가한 작업은 다음 명시적 시작까지 queued로 유지한다. 이는 새 작업 추가가 현재 일괄 실행에 자동 편입되는 기존 동작을 변경하는 결정이다. 사용자가 추가와 실행을 구분할 수 있게 하기 위한 변경이다.
- 새 목표의 계획/시작도 기존 API로 수행한다. 인증/모델 preflight 실패를 화면에 유지하고 실제 지원되는 다음 행동을 표시한다. `/login`을 model prompt로 보내지 않는다.
- 조회 세션의 팀 화면 복귀는 root로 돌아온 후 기본 화면을 연다. 세션 전환 중 handler에서 재귀 대기하지 않는다. 기존 session/view 명령은 유지한다.

## 구현 계약

- controller는 구조화한 active operation(종류, task/check 식별자, startedAt, lastActivityAt, 현재 관찰 상태)을 제공한다. notify, finally, cancel, failure, 체크와 계획 경로를 일관되게 갱신한다. 저장 형식 변경은 꼭 필요한 경우로 제한한다.
- UI는 상태에서 화면 모델을 계산하고 안전하게 렌더링한다. 화면 내 문자열에 제어 문자가 섞여도 터미널 명령이 되지 않게 기존 escaping을 재사용한다.
- custom UI는 fresh snapshot과 render 요청으로 진행 중 변화와 완료를 표시한다. timer/listener는 닫기·세션 전환·reload에 정리한다. detach가 worker/check promise를 취소하거나 버리지 않게 한다.
- 모든 dialog 이후 프로젝트, generation, controller, 작업/attempt 상태, 소유권, trust, busy, recovery를 다시 확인한다. stale selection은 실행하지 않는다.
- 화면 이동 자체로 모델을 호출하지 않는다. 기존 전용 viewer와 CLI/handoff API의 읽기 전용 경계를 보존한다. headless에서 선택을 추측하지 않는다.
- 공개 Pi API와 지원 TUI 컴포넌트만 사용한다. 문서·구현·검증을 일치시킨다.
- 기본 흐름은 동일 세션의 Home → 결과 패널 → Home loop로 만든다. 각 custom UI가 `done(action)`으로 닫힌 후 다음 패널/입력 dialog를 연다. 기존 native 조회 세션은 상세 경로로 유지한다.
- custom UI는 `ctx.mode === "tui"`에서만 연다. RPC의 hasUI만으로 custom TUI를 지원한다고 판단하지 않는다. `session_start`나 `withSession` 안에서 Home loop를 await하지 않는다. native 복귀는 전환 완료 후 fresh context의 명시적 `/teams home`을 `expandPromptTemplates:true`로 보내는 기존 공개 경로를 사용한다.

## 작업 소유권과 검증

Root는 설계·판단·근거·프로젝트 `.pi/settings.json`을 소유한다. 실제 Teams의 Astra high는 이 계약을 읽고 구현 결정을 검토한다. 실제 GPT 6.1 Terra high가 src/bin/tests/package/lock/README/docs/team-sessions.md의 유일한 구현 작성자다. 실제 GPT 6.1 Sol high가 현재 산출물을 독립 검토한다. Normal 요청의 native tier mapping은 미확인이다. 인증과 전역 설정은 변경하지 않는다. commit/push/설치/기존 결과 수락은 하지 않는다.

새 interactive Pi를 테스트용으로 추가하지 않는다. 하나의 작업 Pi에서 계획·구현·검토 후 같은 프로세스의 reload로 최종 UI를 확인한다. 테스트 subprocess는 사용자 창을 만들지 않는다. root가 stable host를 유지하므로 작성자는 프로젝트 실행 설정을 수정하지 않는다.

필수 근거: 기존 184개 회귀 유지, idle 결과 2개/active check/계획·응답·도구·완료·실패·취소·복구·불명확 실행 상태, 취소/빈 입력의 비실행, explicit action, stale dialog와 ownership, 120x30 렌더링과 cleanup. 필요한 의미 있는 새 회귀만 추가한다. typecheck·전체 suite·실제 loader·pack·Node22 lookup 계약을 확인한다. 같은 Pi에서 기본 화면→작업→결과→복귀와 실제 controller check 진행/완료를 확인한다. 소스·자동 테스트·TUI 관찰·사용자 사용성 수락을 구분한다.
