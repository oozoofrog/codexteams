# codexteams launcher design

The user authorized the previously recommended thin launcher: implement `codexteams` to start Pi, form the team, plan and begin eligible work; update installation documentation, test and push. Existing Pi authentication, trust, explicit profiles, recovery and human acceptance remain authoritative. This is v0.2.0; no daemon, automatic acceptance or paid verification calls.

## User behavior

- `codexteams` opens Pi in the caller's cwd and displays current project status without creating project state or calling a model.
- `codexteams "goal"` opens Pi and issues one `/teams launch <goal>` command. That operation reserves the controller across planning and execution, waits for a valid plan, then executes ready tasks until the existing review/failure/cancellation gates stop progress.
- Existing goal/tasks/planning history is displayed rather than automatically replanned or resumed. Profiles-only state may start its first goal. Recovery and owner locks are preserved.
- Goals are literal argv text, never shell code. A blank/oversize goal, unsupported flag, worker recursion, missing/incompatible Pi is reported before launching work.
- The launcher rejects nonempty non-TTY stdin before resolving/probing Pi, so piped text cannot become an unintended model prompt. Empty EOF is allowed. The launcher uses inherited stdin/stdout/stderr, forwards termination signals and returns Pi's exit result. When either stdin or stdout is non-TTY it explicitly selects JSON mode, because Pi text print mode omits extension custom messages. Pi remains the TUI/process owner. No startup intent is attached to session_start, so reload/session replacement cannot replay a goal.

## Installation and loading

Add a packaged Node ESM executable `bin/codexteams.mjs` via package.json bin and files. Install the command from the public Git repository with npm global installation using `--ignore-scripts --omit=dev --legacy-peer-deps`; Pi itself remains an explicit prerequisite (validated >=1.4.0 <2). Existing `pi install URL` still installs only extension resources and is documented separately.

Resolve the host Pi executable from explicit `--pi <executable>`, then `CODEXTEAMS_PI`, then `pi` on PATH; validate `--version` and never silently substitute another executable. Child workers use the same `CODEXTEAMS_PI` selection. The existing resolvePiInvocation behavior remains unchanged when no selection exists.

Run Pi with `--no-extensions -e <this package's absolute src/index.ts> -- <one teams command>`. This dedicated session loads this codexteams version once, even if another copy is registered. It does not rewrite personal settings or auth. Other auto-discovered extensions are intentionally disabled for this session, including extension-provided custom providers; built-in Pi authentication/provider support remains. This tradeoff must be visible in README. Skills, MCP and other Pi settings are not globally rewritten.

## Extension and controller contract

Add `TeamController.launch(goal: string): Promise<RunSummary>`. Planning and queue helpers share the existing implementations with start/run; launch owns one exclusive abort/done reservation for both phases. Add remains blocked during planning and becomes available during worker execution. A cancellation/shutdown between phases cannot dispatch a worker. `launch` refuses an existing goal, tasks or planning history; existing state is never reset.

Add `/teams launch <goal>` as the single explicit startup command. With no goal it behaves as read-only status. For saved project state it displays the board and explains normal run/resume/recover actions. TUI launches run in background to keep cancel available; non-UI command processing awaits launch so Pi print mode cannot exit and abort newly started work. Display completed/failure state for non-UI as well. The existing CODEXTEAMS_WORKER exclusion remains; the launcher also refuses recursion from a worker environment.

- Extension tests prove single explicit launch routing, background TUI cancellation, non-UI awaiting, and no session_start replay.
- Test installed executable packaging and real Pi status/extension loading without credentials. Use a local protocol fixture if actual worker execution is needed; never contact a paid model.
- Preserve all existing regressions, run full typecheck/test suite, actual Pi loader and npm pack checks, independent review, then push main after integration.
